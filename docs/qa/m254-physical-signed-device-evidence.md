# M254 — Real Android devices, signed APK and SQLCipher release NO-GO

## Scope and result today

M253's 25/25 GitHub Actions successes are emulator/software regression evidence on
`1a957d06ce51a9e20b04bfa4856db87e22fafb4f`; they are NOT evidence of two real
Android phones, an independently signed APK bound to the reviewed source, OS key
recovery, portable backup, or authorization to migrate real user finance data.

M254 has **no release job and performs no finance migration**. Its
`scripts/qa/m254_physical_release_evidence_review.py` only compares the
**private, local** output of existing M189 and M190 verification tools and
lists blockers. Even fully consistent files produce **release NO-GO**. Never
commit/upload user data, private keys, ADB serials, raw SMS, receipts, device
logs, PINs or unredacted personal identifiers.

## When the trusted signed candidate is independently available

Do not confuse a GitHub emulator/debug APK with a signed release binary.
The user's previously trusted APK build #705 is also NOT evidence that it
contains M253's new code. Before testing M253 on actual physical devices, an
authorized release/testing process must provide an independently source-pinned
and signature-pinned **non-production** test candidate while retaining #705
as the known-good rollback build. This PR neither creates nor signs it.

1. On a private testing laptop: use two different authorized physical Android
   devices, both attached to ADB. Never use an emulator as a second device.
2. Capture presence-only M189 evidence to a **private** file:
   `python3 scripts/qa/m189_physical_device_source_probe.py --capture --output /private/m189.json`.
   This confirms presence and package name only; it cannot prove that the
   reviewed signed APK bytes are actually installed.
3. Independently pin the APK SHA-256 and signing certificate SHA-256, then
   run `python3 scripts/qa/m190_signed_apk_preflight.py --apk /private/review.apk
   --expected-apk-sha256 <independently-checked-64hex>
   --expected-cert-sha256 <independently-checked-64hex>
   --output /private/m190.json`.
   This does not prove a source commit SHA; that provenance requires separate
   independently verified build records.
4. Compare the two reports offline:
   `python3 scripts/qa/m254_physical_release_evidence_review.py
   --physical-report /private/m189.json
   --signed-apk-report /private/m190.json
   --expected-commit-sha <reviewed-40hex-SHA>
   --output /private/m254.json`.
   The SHA is a *claimed review target*, not an authenticated binary→source
   link; check the report's outstanding blockers.
5. Independent, witnessed **runtime** acceptance must then exercise, on two
   genuine devices with the identical signed binary and tracked installation:
   - no fabricated empty finance source on first install, restart and app/widget start
   - recorded income/expense, confirmed SMS (single and bulk), duplicate and rollback
   - category, goal, recurring, budget, receipt attach/delete/undo and receipt bytes
   - concurrent Home and Widget writes plus process kill during a finance commit
   - independent hardware-keystore key recovery and cold reopen
   - archive export, offline restore on second device, correct counts/hash/receipt
     equality, wrong-password refusal, incomplete/corrupt archive refusal
   - legacy migration parity, safe error/rollback and no silent source downgrade
   - pull-to-refresh regression observed in user-approved build #705: retry must
     not be necessary on ordinary refresh; unreadable/inconsistent source
     MUST still fail closed rather than silently showing stale/missing money
   - delete account, screenshot and crash-reporting consent/privacy review
6. An independent reviewer records a source-linked signer, anonymized
   environment, test steps, recovery evidence and failures in a PRIVATE
   release system. Mere bool values in CI/JSON can never substitute for this.
7. Only after real witnessed tests and privacy requirements are satisfied
   should a human consider approval of a separate production cutover step.

## Hard stop conditions

- Any missing device, mismatched signer/source, untested writer route, corrupt
  receipt byte, migration parity mismatch or unavailable key: **NO-GO**.
- Do not reset, delete, share finance data, invent attestations or activate a
  vault to make tests pass. No new APK is generated by this milestone.
- Never set production flags from M189/M190/M254 reports. Production gates
  remain default-off even if *all* unit tests are green.
